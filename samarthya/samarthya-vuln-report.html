Production API Documentation Fully Exposed

CWE-200 · Information Exposure · api.samarthyaclasses.com
▶

Description

The interactive Swagger UI (/docs), ReDoc UI (/redoc), and raw OpenAPI specification (/openapi.json) are publicly accessible on the production API server without any authentication. This exposes 100+ internal API endpoints, all request/response schemas, authentication mechanisms, admin routes, and security requirements.

Proof of Concept

curl https://api.samarthyaclasses.com/docs           → 200 OK (Swagger UI)
curl https://api.samarthyaclasses.com/redoc          → 200 OK (ReDoc UI)
curl https://api.samarthyaclasses.com/openapi.json   → 200 OK (Full spec)

# Reveals all admin endpoints including:
GET  /api/v1/admin/users          # All user data
GET  /api/v1/admin/enquiries/export  # Student PII export
POST /api/v1/admin/users/{id}/grant-access  # Payment bypass route
POST /api/v1/admin/purchases/{id}/refund    # Refund trigger

Impact

An attacker gains a complete blueprint of the application internals: all hidden admin routes, payload shapes for crafting attacks, and internal field names enabling mass assignment and IDOR attempts. This accelerates every other attack on this list.

Fix Remove or restrict /docs, /redoc, and /openapi.json in production. If needed for development, gate them behind an IP allowlist or admin authentication. In FastAPI: app = FastAPI(docs_url=None, redoc_url=None, openapi_url=None).

Critical

No Rate Limiting — Login Endpoint Allows Unlimited Brute Force

CWE-307 · Improper Restriction of Auth Attempts · api.samarthyaclasses.com
▶

Description

The login endpoint (POST /api/v1/auth/login) imposes no rate limiting, IP-based throttling, CAPTCHA, or account lockout after repeated failures. An attacker can attempt unlimited password combinations against any known email address.

Proof of Concept

# 50 consecutive failed login attempts — all return HTTP 401, never locked
for i in {1..50}; do
  curl -X POST https://api.samarthyaclasses.com/api/v1/auth/login \
    -H "Content-Type: application/json" \
    -d '{"email":"victim@example.com","password":"guess'$i'"}'
done
# Result: 50x HTTP 401 — no lockout, no throttle, no CAPTCHA triggered

Impact

Automated password spraying or dictionary attacks can compromise student accounts containing purchase history and personally identifying information. Combined with the weak password policy (Finding 08), accounts using common passwords like "password" are trivially compromisable.

Fix Implement exponential back-off after 5 failed attempts. Lock accounts temporarily after 10 failures and notify via email. Add CAPTCHA after 3 failures. Rate-limit by IP (e.g. 10 req/min). Use a library like slowapi or Cloudflare rate-limiting rules.

JWT Access Token Not Invalidated After Logout

CWE-613 · Insufficient Session Expiration · api.samarthyaclasses.com
▶

Description

After calling POST /api/v1/auth/logout (which properly invalidates the refresh token), the short-lived access token continues to authenticate requests against all protected endpoints. The server returns a success response for logout but does not maintain a server-side token denylist.

Proof of Concept

# Step 1 — Obtain tokens
POST /api/v1/auth/login → access_token="eyJhbG..." refresh_token="P10Fu..."

# Step 2 — Verify authenticated
GET /api/v1/auth/me  Authorization: Bearer eyJhbG...
→ 200 {"id":6,"email":"vuln_test_comp@mailinator.com",...}

# Step 3 — Logout
POST /api/v1/auth/logout  {"refresh_token":"P10Fu..."}
→ 200 {"success":true,"message":"Logged out successfully"}

# Step 4 — Token still works (VULNERABILITY CONFIRMED)
GET /api/v1/auth/me  Authorization: Bearer eyJhbG...
→ 200 {"id":6,"email":"vuln_test_comp@mailinator.com",...}  ← Should be 401

Impact

If a student logs out on a shared/public device, their session remains live for up to 30 minutes (the token's TTL). Anyone who captured the token (e.g. from browser history, a shoulder-surfer, or a XSS attack) can continue to use it after the user believes they have signed out.

Fix Maintain a Redis-backed JWT denylist (store the token's jti on logout; check it on every request). Alternatively, use very short access token lifetimes (5 min) with opaque session tokens stored server-side.

Missing Content-Security-Policy on Both Domains

CWE-693 · Protection Mechanism Failure · samarthyaclasses.com + api
▶

Description

Neither the frontend (samarthyaclasses.com) nor the API (api.samarthyaclasses.com) sets a Content-Security-Policy header. The frontend also lacks Strict-Transport-Security (HSTS). The API is missing all standard security headers except server: uvicorn.
